La tercera migración a shadcn: por qué esta vez es distinta

ADR-0004 exige que una tercera migración argumente contra las dos revertidas. Esta nota es ese argumento, y el mockup Workfile Shadcn.dc.html es su spec normativo.

Por qué fallaron las dos primeras

Las dos migraciones compartieron el mismo defecto de diseño: coexistencia por capas. El design system bespoke y el generado convivían, los tokens compartían nombre con significados distintos (el --accent de Workfile era un azul de marca; el de shadcn, un gris de hover), y un selector de elemento legacy siempre ganaba la cascada a una clase generada. El resultado documentado en T-0100: dos cards cerradas como done con 36 botones nativos y 3.372 líneas de CSS a mano intactas.

La segunda además dejó que shadcn add escribiera runtime en dependencies, amenazando la garantía publicada de cero dependencias.

Las reglas de esta migración

  1. Sin coexistencia. El stylesheet bespoke se borra en el mismo PR que introduce shadcn. No hay periodo en que dos cascadas compitan; una vista o está migrada o no compila.
  2. El look de shadcn gana, con una excepción nombrada. Se adoptan los tokens zinc de shadcn tal cual (base 14px, radius 0.625rem, sombras xs). Lo único que Workfile aporta son los tokens semánticos --status-*, --priority-* y --sev-*, que shadcn no tiene y que se declaran en un namespace que ningún registry pisa. Nada de re-teñir componentes generados.
  3. Radix, no Base UI. radix-ui ya es devDependency y ya se usa; cada componente de shadcn sigue publicándose para Radix. Cambiar de librería de primitivas a la vez que de design system duplicaría el riesgo.
  4. La garantía de cero dependencias se conserva. Todo lo que instale el CLI se mueve a devDependencies en el mismo commit. dependencies.test.ts no se toca: sigue afirmando que dependencies es exactamente @types/node.
  5. Los tests cambian de bando, no desaparecen. design-system.test.ts se reescribe para afirmar lo contrario: que los componentes viven en components/ui/, que ningún componente escribe un literal de color fuera de los tres namespaces semánticos, y que no queda ninguna clase del vocabulario bespoke (.btn, .chip, .tile…).
  6. Las convenciones de dominio sobreviven al framework. CONV-0003 (native-select en filas de tabla, nunca un select con portal) se implementa con el componente Native Select de shadcn. La densidad de tabla se recupera con la variante compacta, no con un fork del componente.

Lo que se pierde y se acepta

  • La base de 13px. shadcn está diseñado a 14px y forzar la escala reabriría la guerra de cascadas. La densidad se conserva vía la fila compacta de 40px y el toggle cómoda/compacta.
  • El azul de marca como acción primaria. El primary zinc de shadcn asume ese rol; el color vuelve a la UI únicamente por los tokens semánticos, donde significa algo.
  • La lectura top-to-bottom de un único styles.css. A cambio, cada componente es un fichero copiado que se puede editar sin pelear con reglas escritas en otro sitio.
