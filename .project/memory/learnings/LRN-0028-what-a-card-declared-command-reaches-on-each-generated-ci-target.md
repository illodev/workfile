Audited for T-0188 against `packages/workfile/src/modules/ci/ci.ts` at 0.6.0. The three generated targets are `githubBody`, `gitlabBody` and `genericBody`. All three run the same two commands — `doctor --json` and `agents check --json` — and none runs a card's `verify[].run` yet; what follows is what a card-declared command *would* reach once a runner exists, plus what the templates already expose today.

**The premise first: all three targets already execute repository-supplied code, and the allowlist does not touch it.** `loadWorkspace` (`src/workspace/load-workspace.ts:197-203`) does `await import()` on `project.config.mjs` out of the checkout, so every command that loads a workspace runs that file — `doctor` included, the one command the generated workflow exists to run. One hop further and unrecorded until now: `runDoctor` (`src/modules/health/doctor.ts:95-98`) builds an integration registry from that same module's `integrations` export and calls each declared `healthCheck` (`src/modules/integrations/registry.ts:106-107`). So a pull request that edits `project.config.mjs` runs its own JavaScript, and then its own functions, on the runner, with no card involved. LRN-0025 records the first channel; the second is a further one and needs a card of its own.

**GitHub — `.github/workflows/workfile.yml`.** The trigger is `pull_request`, not `pull_request_target`, so a fork's pull request builds the fork's head and GitHub withholds the base repository's secrets from it. *That withholding is the protection, not the permission scope.* `permissions: contents: read` was set at the top level, which means a second job added by hand inherits read rather than starting from nothing — now `permissions: {}` at the top with `contents: read` on the job that needs it. `actions/checkout@v4` defaults to `persist-credentials: true` and writes `GITHUB_TOKEN` into `.git/config` as an `http.extraheader`, where any later `run:` step can read it and use it against the API; on a private repository that is read access to the whole repository with no egress restriction. Nothing in this workflow pushes, so `persist-credentials: false` costs nothing. The `push` trigger lists `main`, `master` and `dev`: a push pipeline runs in the base repository with every secret available, so on a branch anyone with write access can push, the exposure is total and no template setting changes that. There was no `timeout-minutes`; there is now.

**GitLab — `.gitlab/workfile.yml`.** There is no `permissions:` equivalent to emit, and that absence is the finding. A job sees every CI/CD variable not marked *protected*, and the `if: $CI_COMMIT_BRANCH` rule fires on every branch push, so anyone who can push a branch gets them; the remedy is on the variables, not in this file. `CI_JOB_TOKEN` is always present and reaches whatever the project's job-token allowlist permits. The generated file is also inert on its own — GitLab reads `.gitlab-ci.yml`, and nothing in Workfile writes an `include:` — so a project that ran `ci sync` and stopped has no pipeline at all, which reads as "the checks pass" when nothing ran. `image: node:N-slim` runs as root in the container; on a shell executor or a privileged Docker runner that reaches the runner host. The template now carries `interruptible`, `timeout: 10m`, and a header stating each of these.

**Generic — `.project/ci/workfile.sh`, mode 0755.** There is no permission model to review. The script inherits the entire environment of whatever invokes it: a build agent inside a credential block, a self-hosted runner with an instance metadata endpoint, a developer's shell with `~/.npmrc`, `~/.aws` and an ssh-agent socket. Workfile controls none of it, so "run card checks where there are no secrets" is unenforceable here and can only be stated — which the header now does.

**What this means for the allowlist.** It bounds which command a card may *name*; it cannot bound what that command *does*, because every command worth allowing dispatches through a file the same pull request can edit — `pnpm test` reads `package.json`, `node --test` reads the test files, `make check` reads the Makefile. Read it as anti-escalation on a branch you trust, and as keeping a declared command reviewable in one place — the maintainer running `card verify` on a branch they only meant to read is the case it genuinely covers. Containment for a branch you do not trust belongs to the job: no secrets, no write token, and no evidence written back from a head nobody reviewed.

**How to apply.** Declare `cards.verification.commands` as argv prefixes and cut each prefix at the first element that still requires a repository file — `["node", "--test"]` rather than `["node"]`, because `node` alone admits `node -e` and that runs code which is not in the repository at all. Never argue any of this as a fork boundary; LRN-0025 explains why that framing stops people looking for the real one.
