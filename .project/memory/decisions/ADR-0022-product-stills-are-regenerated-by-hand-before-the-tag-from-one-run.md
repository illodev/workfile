`pnpm run screenshots` stays a manual step and does not join the release workflow. Decided by the owner on 2026-09-11 on T-0205.

## Why

- The release job runs after the tag. Stills committed by a bot from that job would land in a commit *after* the one they picture, so the pictures of a version would never live in the version.
- The run needs a browser: 114 MB of Chromium per job, downloaded on every release, for images that change only when the shell does.
- A still should change when the interface changes, not when the version number does. Six of the last releases changed no view; every one of them would have rewritten seven binaries.

## What holds it together

One run writes every copy: the script publishes the seven stills to `.github/media` and `site/assets` itself, so the README and the landing page cannot drift from each other — only, together, from the product. The release circuit in the README names the step: if any UI change shipped since the last tag, run the screenshots and commit the stills with the change that moved the shell.

Revisit if a release ships with stale stills twice: at that point the manual step has failed the way the manual sequence `upgrade` replaced did, and the answer is a check that fails the release when the UI changed and the stills did not, not a bot that commits pictures.
